- 2026-05-31 Task 6 外部/格式研究（Ogg Vorbis comment packet targeting）：
  - Vorbis 头包顺序必须是 identification → comment → setup；可用识别前缀分别是 `0x01 + "vorbis"`、`0x03 + "vorbis"`、`0x05 + "vorbis"`。comment header 是第 2 个头包，且只属于 Vorbis bitstream，不应把别的 Ogg codec 当成本任务目标。证据：
    - https://xiph.org/vorbis/doc/Vorbis_I_spec.html
    - https://xiph.org/vorbis/doc/v-comment.html
    - https://github.com/quodlibet/mutagen/blob/a161810a072ec7f709114fc8a4cac7958693f780/mutagen/oggvorbis.py#L105-L145
    - https://github.com/devsnd/tinytag/blob/01363dc81fa7f391ca2a4f3bbb82dc24b9a35b0e/tinytag/tinytag.py#L1473-L1500
  - Vorbis comment packet 布局是：`vendor_length(u32 LE)` → `vendor_string` → `user_comment_list_length(u32 LE)` → 每条 `length(u32 LE)` + `comment bytes` → 末尾 `framing_bit=1`；comment 内容按 `KEY=VALUE` 的 UTF-8 向量编码，字段名不区分大小写。证据：
    - https://xiph.org/vorbis/doc/v-comment.html
  - Ogg 逻辑流/页基础约束：page 以 `OggS` 开头，`bitstream_serial_number` 用来区分逻辑流，`page_sequence_number` 只在同一逻辑流内递增；`header_type_flag` 的 `0x01` 表示续页承载上页未完 packet，`0x02`/`0x04` 分别是 BOS/EOS。Ogg 的 segment table（lacing values）只负责把 packet 切到页里，packet 可能跨页。证据：
    - https://xiph.org/ogg/doc/oggstream.html
    - https://xiph.org/ogg/doc/rfc3533.txt
  - 对 Task 6 的安全建议：只对单个目标 serial 做最小状态机扫描；忽略其它 serial 的页面和 packet；遇到非 `OggS`、version≠0、header 前缀不是 `vorbis`/`vorbis` 时立即跳过或停止当前流解析；对页数、已扫描字节数、当前 packet 累积字节数继续保留上限，避免无界跨页拼接。不要扩展到 Opus/Theora/混合视频流或通用 chaining 处理。参考的真实实现也都只在匹配 serial 后收集 Vorbis comment packet，并直接去掉前导 `vorbis` 解析：

    - https://github.com/devsnd/tinytag/blob/01363dc81fa7f391ca2a4f3bbb82dc24b9a35b0e/tinytag/tinytag.py#L1473-L1500
  - Task 6 最小 per-serial 状态建议：`serial`、`stage`(expect ident/comment/setup)、`packet_buf`、`packet_bytes`、`page_count`、`scanned_bytes`、`seen_comment`、`done`。这样可以支持定向 Vorbis comment 抽取，而不需要实现完整 muxer / chaining / seek 支持。
- 2026-05-31 Task 8: MP4/ISO BMFF `size=0` 语义与安全恢复边界
  - 规范/准规范共识：`size=0` 表示该 box 的内容延伸到“其所在容器(scope)的末尾”；在官方/实现文档里通常表述为“box extends to end of file”或“last box in that container”。ISO BMFF 参考实现/SDL 片段写明 `size==0` 时 box extends to end of file（通常只用于 mdat），W3C MSE 讨论也明确说 `size=0` 的 box 必须处于 top-level container，且是该 container 的最后一个 box，payload 才能延伸到 container 末尾。证据：Bento4 `Ap4AtomFactory.cpp` 197-209，`Ap4LinearReader.cpp` 374-383；W3C issue #8 对 size=0 的澄清；FFmpeg `mov_read_mdat()` 1401-1405 直接把 size==0 的 mdat 视为“wrong one (MP4)”并拒绝按普通 mdat 处理。
  - bounded parent 规则：`size=0` 不能“穿透”已知父盒边界。若当前 parser 已有父范围 `limit`，则 `size=0` 只能解释为“到当前父范围末尾”，前提是它是该父范围内最后一个 child；若该 child 后面还存在兄弟 atom，则该 `size=0` 视为 malformed，而不是把后续隐藏兄弟一起吞掉。TagReader 现有 MP4 walker 也采用父范围约束：`WalkMp4IlstItems()` 只在 `childOffset < atom.atomEnd` 时才下探，且 `ReadMp4AtomPayload()` 只按 `atom.payloadOffset..atom.atomEnd` 读取，不越界。证据：`src/TagReader.cpp` 2510-2579、2610-2624。
  - 安全恢复建议：当 `size=0` 出现在 bounded parent 的中间位置时，不要继续用“无限延伸”解释；应立即把该 atom 标记为 malformed，停止对该分支的递归下探，并仅在当前 parent 的剩余范围内做有限、资源受限的重定位/试探，以便在 locator boundaries 明确、且不会跨出 parent 末尾时，仍有机会找到后续合法 sibling metadata。若不能在父范围内安全恢复，则放弃该子树而不是扫描到父范围外或文件尾。
  - 资源上限建议：保留 `kMaxMp4Atoms`、`kMaxMp4AtomPayloadBytes` 一类上限；对 `size=0` 分支额外要求“remaining bytes <= parent remaining && <= payload limit”，否则直接判 malformed 或 resource limit，避免无限扫描/巨量读取。
